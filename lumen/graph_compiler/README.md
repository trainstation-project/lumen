# `lumen/graph_compiler`

The graph compilers: they take a traced [`Graph`](../graph/) and turn it
into a [`Plan`] — an ordered list of kernel launches (`Step`s) with every
value placed in one workspace. This is lumen's XLA analogue: a
device-independent frontend (CSE, algebraic simplification), then one
compiler per device (`mps/` fuses into generated Metal kernels; `cpu/` runs
the primitives as they are), then buffer assignment and scheduling in
`plan.rs`.

`lumen.compile` (`lumen/graph/tracer.py`) builds `lumen.graph_compiler.Plan`
objects and caches them; `lumen.config.compiler` holds the flags they are
compiled with. Kernels themselves live in `lumen/ops` (primitive kernels) and
`lumen/codegen` (generated fusion kernels); this folder decides *what* runs
and *where it lives in memory*.

## Subfolders

- [`passes/`](passes/README.md) — the device-independent passes (`cse`, `simplify`, pattern rewrites), each a `CompilerPass` of any module.
- [`cpu/`](cpu/README.md) — the host compiler (one `simplify` pass, then plan).
- [`mps/`](mps/README.md) — the MPS compiler: fusion passes, Metal codegen driving, `encode`.
- [`mps/ane/`](mps/ane/README.md) — optional Apple Neural Engine offload through Core ML.

## Compile flow

```text
compile_with(graph, device, options)
  ├─ Pipeline "frontend": cse → simplify            (every device)
  ├─ device != Cpu(0) and the graph has host values → stages::compile → staged Plan
  └─ device_compile(without_transfers(graph))
       ├─ Device::Mps → mps::compile                 (only with cfg lumen_mps_linked)
       └─ otherwise   → cpu::compile
```

Each device compiler runs its own `Pipeline`, then calls
`Plan::compile_with(graph, &PlanOptions)`.

### `Options` and `CompilerConfig`

`Options` is what one compile takes: `config` (a `CompilerConfig` snapshot,
by default `config::config()`), `donate`, `donate_into`, `parameters`,
`packable` and `scalars` (the last three are per-input masks). Device
compilers translate them into `PlanOptions` (positions, scratch fn,
`memory_limit`, packed `blocks`).

`CompilerConfig` is a process-wide `RwLock` read once per compile; changing
it (`update`, or a setter on `lumen.config.compiler`) affects future
compiles only — already-built plans keep theirs. Defaults run programs
exactly as traced **except** `online_softmax`, `flash_attention`,
`fused_linear_cross_entropy` and `split_k`, which are on and change rounding
order. `deterministic`, `neural_engine`, `safe_kernels` are off;
`memory_limit` is 0 (no limit); `dump_to` is `None`. Every field's doc
comment in `config.rs` is the authoritative description. Python setters are
generated by the `flags!` macro in `python.rs`, so a new flag needs an entry
there too.

### Passes (`pass.rs`)

- `Module` — what a pass rewrites (graph + options). `GraphModule` is the
  plain one used by the frontend and CPU; MPS has its own `MpsModule`.
- `CompilerPass<M>` — the pass interface every pass implements: `name()` +
  `apply(&mut M)`. A pass of the graph alone (`passes/`) implements it for
  any `M: Module`, so every device's pipeline can run it; a device's pass
  implements it for its own module (`MpsModule`).
- `Pipeline::new(name).add(..).run(&mut module)` — runs passes in order,
  each inside a profiler range `<pipeline>::<pass>`.
- **`dump_to`**: with `lumen.config.compiler.dump_to = dir`, each pipeline
  run writes `dir/<id:04>.<pipeline>.<step:02>.<pass>.txt` — step `00` is
  `input`, then one file after each pass. `<id>` is a process-wide counter
  per pipeline run.

### Plan (`plan.rs`)

`Plan::compile_with` plans the graph in three orders (the trace's,
`schedule::list`, `schedule::dfs`) and keeps the smallest workspace (ties
keep the earlier). If that still exceeds `memory_limit`,
`remat::rematerialize` recomputes values at later readers, measuring each
candidate by planning it.

Within one order (`compile_in_order`):

- **Liveness / dead code**: only nodes reaching an output become steps.
- **Buffers** (`Buffer`): `Input(i)`, `Output(i)`, `Workspace(offset)`,
  `Scalar(i)` (a one-element runtime scalar passed by value, never copied
  to the device).
- **Views and placements**: a `reshape` is its operand's bytes; a slice
  marked `view` is a strided view of its operand; operands of a concatenate
  marked `in_place` are written at their slot of the result. All come from
  `Graph::placements()`; steps record them in `views` / `output_views`.
- **In-place reuse**: `dynamic_update_slice`, `scatter_add` and custom ops
  write over their operand where it dies; other steps may take a dying
  operand's bytes when they read it elementwise (XLA's
  `CanShareOperandBufferWithUser`). Core ML steps never do.
- **Donation**: an output takes a donated input's buffer (same type, nothing
  reads the input after). `donate_into` pins one output to one input.
  Packed `blocks` delay a member's donation until no step reads its block.
- **Workspace**: values without a buffer and each step's kernel scratch
  (`PlanOptions::scratch`, alive for that step only) are packed largest
  first at the lowest free offset, aligned to `ALIGNMENT` (256).
- **Owned plans** (`parameters: Some(..)`): outputs live in the workspace;
  `run_in(workspace, inputs)` reads parameters in place and returns views
  valid until the next run.

`Plan::run` runs on the inputs' device (MPS steps through `lumen/ops/mps`,
TPU steps through `lumen/ops/tpu` (dots, merged dots' fusions,
elementwise primitives and `reduce_sum`: any other step errors), elsewhere on the host); `run_on` takes an explicit device (meta runs
nothing). `print(plan)` shows each step as `out:type = primitive in...`.

### Stages (`stages.rs`)

When a program on a device has values moved with `to_host`, `place` tags
each value Host / Device / Free (scalars and constants). An op reading both
sides is an error ("Expected all tensors to be on the same device ...").
Values are grouped into stages that alternate device (even) / host (odd);
each stage is compiled by its side's compiler and the result is a `Plan`
with `staged: Some(..)` whose device stages share one workspace side by
side. Programs with no host values return `None` and compile normally.

### Attention matching (`attention.rs`)

`attentions(graph)` finds `softmax(q @ k^T * scale [masked]) @ v` however
written (casts, causal `iota` masks, dropout via `random_bits`, GQA
broadcasts, slices of merged dots), requiring float32 accumulation. Used by:
`mps/flash_attention*.rs` (`fuse`, `fuse_backward`), `lumen/codegen/mps`
(`Attention`, `Backward`, `Access`, `Score`, `Dropout`), and the tracer
through `traced` (`lumen.Graph.attentions`), which replaces each match by
one node whose backward is FlashAttention-2's. `MAX_HEAD` (256) and
`MAX_BACKWARD_HEAD` (128) bound the head dimension.

### Python (`python.rs`)

`Plan(graph, device=None, fuse=None, donate=(), parameters=None,
packable=(), scalars=(), donate_into=())` validates input positions,
snapshots the config (with `fuse` overriding it) and calls `compile_with`.
Exposes `workspace_bytes`, `packed`, `neural_engine`,
`_invalidate_neural_engine`, `steps()` (dicts with buffers, views, scratch,
scope, sources), `run`, `run_in`. `lumen.config.compiler` is returned by
the `Config` class in `lumen/allocator/python.rs`.

## Invariants & gotchas

- Graphs are pure: CSE and simplification must never change results.
  Anything that changes rounding belongs behind a config flag, off unless
  listed above as on.
- `simplify` (frontend) runs with `matched = false` so patterns (attention,
  linear cross entropy) are still in traced form when MPS matches them; the
  MPS and CPU pipelines rerun it with `matched = true` afterwards.
- Every rewrite builds a new graph and must call `set_origin` per node so
  `Step::sources` / `scope` (profiler ranges, source lines) survive.
- `Pipeline::run` with `dump_to` writes files — a write error fails the
  compile.
- `mps` is compiled only with `cfg(lumen_mps_linked)`; `attention.rs` is
  `allow(dead_code)` elsewhere.
- Planner behavior is measured, not estimated: changes that add steps or
  views must keep `plan_tests.rs` green (workspace sizes are asserted).
